# Maps Scale and Cloud Reliability QA — 2026-08-05

## Change

Direct revision-controlled cloud uploads below the 16 MiB resumable threshold now recover from a lost final response by verifying the provider's new revision, exact byte size, and content hash. The provider-independent helper never blindly repeats an ambiguous write. New-file adds remain unchanged because an autorenamed destination cannot be proven safely without a returned path.

## Synthetic baseline and result

No Dropbox credentials or real files were used. Mocked, non-sensitive payloads represented approximately 1,000, 10,000, and 40,000 features at 1, 8, and 15 MiB.

| Features | Payload | Baseline after committed response loss | Result | Uploads | Metadata verifications |
| ---: | ---: | --- | --- | ---: | ---: |
| 1,000 | 1 MiB | False failure | Recovered | 1 | 1 |
| 10,000 | 8 MiB | False failure | Recovered | 1 | 1 |
| 40,000 | 15 MiB | False failure | Recovered | 1 | 1 |

The broader 1k/10k/50k benchmark covers startup/import, pan/zoom, rendering, serialization/autosave, export, memory, and recovery. On this run, the 50k / 30.44 MiB case measured 48.46 ms startup, 54.93 ms import, 4.62 ms pan/zoom, 0.86 ms rendering, 76.81 ms autosave, 56.14 ms export, 32.10 ms recovery, and 60.91 MiB serialization heap growth. Quota failure preserved the prior stored bytes.

## Compatibility, integrity, and rollback

- Project schema, serialized bytes, cloud paths, OAuth, provider configuration, and stale-revision conflict behavior are unchanged.
- Only revision-controlled Dropbox updates below 16 MiB use recovery verification. Non-retryable auth, quota, and conflict failures still fail immediately.
- A result is accepted only when Dropbox reports a changed revision, exact size, and exact content hash. If verification is unavailable or inconclusive, the original retryable error remains visible and prior local/remote data is not overwritten by a second request.
- Roll back by reverting the single implementation commit; no migration or cloud cleanup is required.

## Exact human verification

Using only an approved disposable Dropbox account:

1. Connect, list, open, save, rename, disconnect, and reconnect a synthetic project smaller than 16 MiB.
2. During a revision-controlled save, let Dropbox commit and then interrupt only the upload response; confirm the UI reports success after one metadata lookup and makes no second upload.
3. Reopen the file and compare feature count, geometry, nested attributes, style, schema, and revision metadata.
4. Repeat with a stale revision and confirm a conflict is shown without treating unrelated current metadata as the saved result.
5. Exercise offline/retry, auth, and quota failures; confirm inconclusive verification retains the error and the current local project plus prior remote revision remain intact.
6. Recheck a new-file add with a lost response; confirm it fails safely rather than guessing an autorenamed destination.
